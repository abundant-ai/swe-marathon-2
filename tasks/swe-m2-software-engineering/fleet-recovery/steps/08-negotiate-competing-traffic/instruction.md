# Renegotiate traffic when two couriers compete for a crossing

Extend `/app/fleet_recovery` so two responsive couriers can share a crossing with a carrier that already has a committed moving prefix. An adapter can delay its own job while another adapter replaces the carrier's future route. A courier waiting for the whole crossing to empty may miss the deadline even though it could already move to the marked holding point. Plan both couriers together, preserve the carrier's committed motion, and release the protected leg only after observing progress on both current itineraries.

Keep the previous commands working. Separate the traffic model, scheduling, movement authority, and durable state in focused modules. Use the installed Open-RMF traffic library for native trajectories and collision checks and reconcile responsive proposals through its negotiation API. The existing `/app/example/rmf` contains a build example for the native library.

## Command and persistence

Run `python3 -m fleet_recovery rmf-negotiate --site SITE.json --state STATE.json --event EVENT.json --output REPLY.json`. Each invocation processes one event. The adapter can restart it between all events. Use a new state file to start a mission. Persist accepted revisions, proposals, outstanding revocations, progress, issued commands, and request receipts. Commit the state and receipt before publishing the reply. Retrying the same request ID and exact JSON event must return the original reply, even after later requests. A reused request ID with changed content or an invalid event is an error with no state change. A logical request is applied once. The adapter deduplicates replayed commands by participant, plan and leg. The caller issues one request at a time.

All times are nonnegative integer nanoseconds in the same mission clock. First-seen requests have nondecreasing `now_ns`. Poses are finite `[x_m,y_m,yaw_rad]` arrays. Use the native trajectories from `rmf_traffic::agv::Interpolate::positions` with the participant's velocity and acceleration limits. The supplied moves are straight between poses with constant heading and come to rest at every named waypoint. Start and goal positions remain occupied when a participant is waiting. A plan leg acknowledges completion at its native finish time, with a tolerance of 10 ns for reporting rounded finish timestamps. Touching circular footprints is a conflict. Check swept motion and waits over the mission horizon. A request can span at most 128 departure slots.

## Site and event records

`SITE.json` contains `map`, positive integer `slot_ns` and `max_time_ns`, and `couriers`, an object keyed by distinct participant ID. It has exactly two courier records. Each record contains `home`, `goal`, `stage` (a pose for one courier, null for the other), and `profile`. The `carrier` record has the same fields and a separate `id`. Its `stage` is a pose. Each profile has positive numbers `radius_m`, `linear_velocity_mps`, `linear_acceleration_mps2`, `angular_velocity_radps` and `angular_acceleration_radps2`. The carrier's schedule starts from `home` at zero, drives to `stage`, waits there until `carrier_tail_ns` and drives to `goal`. Only the future departure from its stage can change. Keep the first motion identical across revisions.

The site has two `guards` for the staged courier's protected crossing, one for the direct courier and one for the carrier. Each has `participant`, `axis` (0 for x, 1 for y), `sign` (1 or -1), and `position_m`. A guard is satisfied at a measured checkpoint whose coordinate passes `sign * (coordinate - position_m) >= 0`.

Each event has `request_id` and `now_ns`. It may include these fields:

- `patch` is `{base,version,mode,carrier_plan,carrier_tail_ns,jobs}`. `base` is null for a full snapshot or an integer for a delta. Every patch carries the full field values. The version starts at 1 and increases. Apply a newer delta only if its base matches the last accepted version. A gap makes the schedule stale until a newer full snapshot or a delta from the actual cursor restores it. Ignore versions at or below the accepted cursor. The carrier's positive integer plan ID changes with its tail replacement. `jobs` maps each courier ID to `{ready_ns,deadline_ns,priority}`. Priority is an integer and higher values are more urgent. The mode is `normal` or `protected`. The fixture supplies applicable schedule changes before either courier has started a leg. The carrier may already be moving.
- `cancelled` is an array of `{participant,plan,pose}` confirmations. After a replacement, treat previous courier plans as outstanding until each original positive integer plan ID is confirmed cancelled at its home position. Use a planar tolerance of `1e-6` m. Repeated, mismatched, or false-position confirmations leave the relevant revocation pending. Issue no replacement movement commands while either confirmation is missing.
- `progress` is an array of `{participant,plan,checkpoint,pose}` observations. The checkpoint is a zero-based index of a native trajectory waypoint, across all route legs with identical boundary times merged. Courier itineraries first include a stationary home waypoint at time zero. Include each motion leg's native waypoints, including its start and finish. The carrier itinerary starts with the first native motion at zero. The stationary hold after the last motion never adds a checkpoint. Accept progress only for the current plan, with a nondecreasing checkpoint index, a measured planar pose within `1e-6` m of the waypoint, and `now_ns` at or after its time. On the staged courier, require an observed stage arrival before crossing. Old plan reports, mismatched positions, early timestamps and earlier checkpoints do not release a guard.

## Plan and issue authority

With a fresh schedule and settled revocations, choose collision-free departure times on the `slot_ns` grid at or after current time and each job's ready time. The `normal` mode uses a direct home-to-goal leg for each courier. The `protected` mode routes the staged courier home-to-stage and then stage-to-goal, and the other courier travels directly. The protected crossing cannot be planned before the first predicted native waypoints that satisfy both guards or before the staged courier reaches the holding point. Its command still requires actual progress reports for all three participants on their current plans. The staged courier may safely approach the holding point while the other participants retain crossing authority.

Require every route to finish by its job deadline and at or before `max_time_ns`. Among joint feasible schedules, minimize the vector of courier finish times in descending priority order, breaking priority ties by ascending participant ID. Break remaining ties by any safe approach timing. If no joint schedule can meet the deadlines, return blocked and issue no legs. Commands authorize the specified whole leg at its planned times. On publishing a new plan, issue the first leg for both couriers. Issue the protected leg once all dependencies are confirmed at or before its planned start. If a confirmation arrives later, withhold the protected command and report blocked. Maintain plan IDs across events and allocate new positive IDs for replacement itineraries so stale progress cannot apply to them.

Write the reply as `{status,version,plan,revoke,commands}`. The integer version is the last accepted schedule cursor, or null before its first snapshot. Status is `stale` on a gap or before the first full snapshot, `awaiting_cancel` during cancellation, `blocked` when no safe plan can run, and `scheduled` while a safe plan is active. The plan is null unless status is `scheduled`. Its object keys are courier IDs and each value has `plan` and `legs`. A leg has `{from,to,start_ns,end_ns}` with the waypoint names `home`, `stage`, and `goal`. On first accepting a newer applicable patch with active plans, include `{participant,plan}` revocations for both couriers. Later fresh requests do not repeat those revocations. Each new command has `{participant,plan,leg}`, where `leg` is the zero-based index in that itinerary. Return empty arrays when no revocation or command is issued.
