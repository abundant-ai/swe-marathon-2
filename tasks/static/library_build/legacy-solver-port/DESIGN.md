# legacy-solver-port: full design (v3)

Status: design complete on paper, **nothing built or validated**. Every number below marked (TUNE) is a first guess that must be calibrated with trials. Companion to `README.md` (rationale, novelty, hackability).

## 1. Decisions that close the open questions

| Question | Decision | Why |
|---|---|---|
| Real or synthetic legacy code | **Synthetic**, written by us in Fortran 77 style (no license risk, couplings controllable) | A real code risks license and contrivance claims; we write it to look like typical 1990s academic CFD |
| Hardware | **CPU only**, 8 cores, no network | Simple to verify, deterministic timing in a fresh container |
| Step 2 | **Scripted** (fixed requirements) | Dynamic simulated collaborator is out of scope for v1 of the task |
| Hidden state in restart (step 4) | Legacy READ routine resets the time-step controller on restart; this is observable only by reading the Fortran | The "continue as the legacy would have" behavior must be reverse-engineered |

## 2. The legacy system (what we must write)

Single-package Fortran 77, target size about 6-10k lines (TUNE; larger raises difficulty, see section 9).

Physics and numerics: 2D incompressible Navier-Stokes, staggered (MAC) grid, Chorin projection, donor-cell/central blended convection (parameter gamma), explicit time stepping with CFL-controlled adaptive dt, pressure Poisson by lexicographic SOR with a residual tolerance. Input decks are namelist-style text files. Output: fixed-width text field dumps at checkpoints, plus unformatted sequential binary restart files.

Planted couplings (each is realistic legacy practice, none is a trap in isolation):

| ID | Coupling | Affects step |
|---|---|---|
| C1 | Boundary conditions are applied inside the stencil and SOR loops via an integer cell-flag array, with the lid speed read from a COMMON block | 2 |
| C2 | All fields and scratch arrays live in COMMON blocks; subroutines read and write them implicitly; SOR sweep order affects the iterates | 3 |
| C3 | dt controller keeps a smoothed history (previous dt, running max velocity) in COMMON, not written to restart files | 4 |
| C4 | Restart READ routine silently reinitializes that history to defaults and applies a one-step warm-up | 4 |
| C5 | Reductions (max velocity, residual norms) are done in loop order, so a parallel port changes round-off | 3, 4 |

Reference data are generated by compiling and running the real Fortran in our build environment, never by the agent's environment. The candidate image ships Fortran **source only**, with no Fortran compiler.

## 3. Candidate environment

- `/workspace/legacy/`: Fortran source, 3 example decks, one example restart, no tests, no docs.
- `/workspace/solver/`: empty at step 1; then the agent's own code (carried over).
- Tools: a modern language toolchain (Python + NumPy + Numba and Rust, or C++; agent's choice), `perf`, standard profilers, 8 cores. No Fortran compiler, no network.
- Deterministic time limit per step (TUNE): step 1 and 2 about 2 days of agent time each, step 3 about 1.5 days, step 4 about 1.5 days. Total target about a week.

## 4. Step specifications

### Step 1: Port and validate
Deliver a CLI in `/workspace/solver/` reproducing the legacy output layout.

Hidden cases (about 30, TUNE):
- Lid-driven cavity at several Re and grid sizes; channel flow; different gamma and tau; non-square grids; varying SOR tolerance and omega.
- Cases sampled at verification time from a parameter distribution, so memorizing visible decks does not help.

Checks:
1. Field agreement with Fortran reference at checkpoints: relative L2 error <= 1e-6 (TUNE) per field.
2. Observed convergence order on three-grid series equals the legacy's (within 0.1).
3. Discrete divergence max <= 10x the pressure tolerance at every checkpoint.
4. `NOTES.md` programmatic probes (see section 6).

### Step 2: New boundary conditions
Add open outflow (zero-gradient velocity, p = 0) and moving wall (arbitrary tangential velocity on any wall), per-boundary from the deck.

New hidden cases (about 12):
- Couette flow with a moving wall (analytic solution).
- Pressure-driven channel with inflow profile and outflow (analytic Poiseuille at the outlet).
- Backward-facing step with outflow (reference reattachment length from our refactored reference solver).

Checks: analytic errors below thresholds (TUNE); new-case agreement with reference; **all step-1 cases still pass**.

### Step 3: Performance and parallelism
Speed up on hidden large grids (for example 512^2 and 1024^2, TUNE) using the 8 cores.

Checks:
1. Accuracy gate: all earlier and new cases within max(1e-6, 50 x solver tolerance) of reference (a parallel solver legitimately changes iterates inside the tolerance).
2. Speed score s = clip(log2(T_base / T_cand) / log2(S_target), 0, 1), where T_base is the verifier-measured time of the verifier's own single-thread reference port (same container, same run) and S_target = 8 (TUNE).
3. Speed counts only if the accuracy gate passes.
4. Thread-count determinism: results on 1 and 8 threads must agree to 1e-10 (this is what makes step 4 solvable; stated in the step 3 instruction as a requirement for later restartability).

### Step 4: Restart-format migration
Read legacy binary restarts, continue as the legacy would have, then write a versioned documented format.

Hidden checks:
1. For each legacy restart file (about 6), continue for N steps and compare to the Fortran continuation: error <= 1e-6 (TUNE). This is where C3 and C4 are decisive.
2. Round trip: write new-format restart, read it back, continue: result must be **bitwise identical** to an uninterrupted run, under 1 and 8 threads (needs the step 3 determinism).
3. Version handling: old files readable; a file with an unknown future version is rejected with a clear error (tested with fixtures).
4. Long run (about 10^5 steps, TUNE): divergence and conserved-quantity drift stay below thresholds; no NaN.
5. All earlier-step cases still pass.

## 5. Dependency map (the contribution)

| Shortcut taken at | Looks fine at | Fails or costs at | Mechanism |
|---|---|---|---|
| Literal port of C1 | Step 1 | Step 2 | BC logic cannot be extended without rewriting the sweep |
| Literal port of C2 and C5 | Step 1-2 | Step 3 | Global state blocks parallelization; parallel round-off then breaks bitwise checks |
| Ignoring C3/C4 (restart behavior) | Step 1-3 | Step 4 | Continuation diverges from legacy |
| Non-deterministic reductions in step 3 | Step 3 | Step 4 | Bitwise round-trip check fails |

Dependency validation protocol (must pass before acceptance):
1. Write solution A (literal port) and solution B (refactored: explicit state, separate BC layer, deterministic reductions, notes). Both pass step 1.
2. Run the continuation on both with the fixed step 2-4 instructions.
3. Required evidence: step 1 scores differ by <= 0.05; A's later scores or agent effort are clearly worse. Effort measured in number of agent actions and tokens, not wall-clock.
4. Repeat with a third independent solution C.
5. If the gap is small, redesign or drop.

## 6. Reward formula (draft, TUNE)

For step k in {1,2,3,4}:
- N_k = weighted mean of new-case checks in step k, each in [0,1], with a **fixed denominator** (a skipped or failed case counts as 0, never removed).
- Reg_k = weighted fraction of all earlier-step cases that still pass at step k (Reg_1 = 1).
- S_k = N_k x Reg_k. Step 3: N_3 = a x s + (1 - a) x acc_pass, with a = 0.7 and N_3 = 0 if the accuracy gate fails.

Total shaped reward R = sum_k w_k S_k, with w = (0.2, 0.25, 0.25, 0.3) (TUNE; later steps weigh more so dependency consequences matter).
Binary reward = 1 iff every S_k >= 0.9 (TUNE). Evaluation errors or missing artifacts give no valid reward. Each term is linked to its implementation and boundary tests in `steps/<k>/tests/`.

`NOTES.md` probes (programmatic, no LLM): the notes must list the state variables the scheme carries; the verifier reads a machine-checked `STATE.json` the agent writes alongside, then checks that perturbing each listed variable changes the output and that no unlisted variable does (via the verifier's own instrumented reference). Worth at most 10% of step 1 (TUNE). Risk: may be too contrived; evaluate in trials.

## 8. Hackability (expanded, see README for the table)

Additions specific to this design: shipping a precompiled legacy binary inside the agent's output (scan for ELF, shared objects, forbidden calls and for large embedded binary blobs); replaying visible-deck outputs (hidden randomized decks); tampering with `STATE.json` to satisfy the probes (probes use the verifier's own instrumented reference, not the agent's claims); reading the verifier timer in step 3 (timing inside the verifier container, measured on its own process tree).

## 9. Difficulty levers and the honest week-long question

An expert is likely to do a 6-10k line 2D code in one to three days, so a week of agent time is **not** guaranteed by this scope. Levers, in order of preference:
1. Enlarge the legacy code (more physics: energy equation, turbulence closure, variable properties) and the hidden-case matrix.
2. Move to 3D with a staggered grid and a multigrid-free SOR baseline.
3. Add a fifth step: MPI-style domain decomposition with bitwise-reproducible restart.
4. Tighten step 3 targets.

Decision rule: after the first full trials, if the median strong-agent horizon is below 3 days, apply levers 1 and 3 before submission.

## 12. Build status (2026-11-17): Fortran legacy code v0 written

Location: `legacy/` (8 source files plus `common.inc`, `Makefile`, `decks/cavity100.in`). About 450 lines. Compiles with gfortran (installed in an isolated conda env for development only; the candidate image ships source and no compiler). Flags `-O2 -ffp-contract=off -std=legacy -ffixed-line-length-none` so results do not depend on FMA contraction.

Implemented: staggered grid, Chorin projection, blended donor-cell convection, adaptive dt controller with history (C3), SOR in lexicographic order with BC coefficients inside the sweeps (C1, C2, C5), unformatted restart that omits the controller state and warm-starts on read (C4). BC types: no-slip, free-slip; lid speed on the top wall only.

Checked:
- 32x32 lid-driven cavity, Re=100, ran to T=20 without NaN. Centerline extrema vs Ghia et al.: u_min -0.190 (ref -0.211), v_max 0.165 (ref 0.175), v_min -0.230 (ref -0.245). About 10% coarse-grid deviation, plausible for a blended donor-cell scheme on 32^2; not refined further.
- Restart read works. A run restarted at step 500 differs from the uninterrupted run at step 1000 by relative L2 2.7e-6 in u (so C4 has an effect, but it is small).

Findings that change the design:
1. **The C3/C4 effect is weak** (2.7e-6) and would sit near the proposed 1e-6 tolerance, so step 4 would barely separate right from wrong. Strengthen before accepting: restart during the fast transient, increase the warm-up reduction and SMOOTH, and use a quantity that compounds (for example the time-step sequence after restart, written to the output). Tolerance for step 4 must be set from measured effect sizes.
2. **No inflow or outflow in the legacy code.** Step 1 cases are cavity variants only (lid, free-slip walls, aspect ratio, Re, gamma, tau, SOR settings). Inflow and outflow arrive together in step 2 (Poiseuille and backward-facing-step cases), which also makes step 2 a larger extension. DESIGN section 4 step 1 "channel flow" should read "cavity variants".
3. Not yet done: the pressure-Neumann/inflow coupling check for step 2, a convergence-order test, the reference-output generation scripts, the 3-4 more decks, and any larger legacy code (section 9 levers). Current code is far below the 6-10k lines targeted.
4. Large-grid memory is static (MX=1026, about 50 MB of COMMON); grids above 1026 need a recompile.

### 12.1 Restart coupling strengthened (2026-11-17)

Change: on restart the step controller history is reset (as before), and now the first 20 steps are ramped (dt scaled by k/21, k = 1..20) instead of one halved step; default SMOOTH raised from 0.5 to 0.9 so the reset history keeps influencing dt for many steps. Files: `legacy/tstep.f`, `legacy/io.f`, `legacy/readin.f`.

Measured (32x32 cavity, Re=100, restart at step 100 in the transient, compare at step 300): uninterrupted T = 3.6422, restarted T = 3.3547 (8% apart); relative L2 difference u 1.1e-2, v 1.5e-2, p 7.3e-3. This is about 4 orders of magnitude above the 1e-6 tolerance, so a port that ignores C3/C4 fails step 4 clearly, while a port that reproduces them can match to round-off.

Step 4 must compare both fields and T (and the dt sequence) at equal step counts, with the restart taken in the transient. The old step 1 cases and the 2.7e-6 measurement in section 12 are superseded. Not yet checked: that a Python port reproducing C3/C4 actually matches to the intended tolerance, and robustness of this effect across Re and grid size.

### 12.2 Solution A (literal Python port) result (2026-11-17)

Files: `experiment/solution_A_literal/nsflow.py` (about 330 lines, pure Python, same module-level state, same loop and operation order), `scripts/compare_to_fortran.py`. Not shipped to candidates.

Compared against the Fortran reference on four cases (16x16 cavity 200 steps; 24x16 non-square, Re=400, free-slip W and S, other gamma/tau/omega, 150 steps; 16x16 run to step 100; restart from that Fortran restart file continued to step 300). Result: **bitwise identical** fields, T, and restart files (byte-equal) in all four cases. Pure Python is too slow for grids beyond about 32x32, so large-grid comparisons were not run.

What this shows:
1. The reference is deterministic and portable: a different language reproduces it exactly when the operation order is preserved (confirms `-ffp-contract=off` was the right call).
2. A literal port needs no numerical understanding, so **step 1 with a 1e-6 tolerance is too easy to hit for a literal port**. Tolerance policy needs rethinking: the discriminating quantity is not step-1 accuracy but what a port can do in steps 2-4.
3. **C3/C4 do not punish a literal port.** It copies the restart reset and ramp automatically, and the restart file layout is readable from `io.f`. Step 4's restart check therefore punishes only a clean-room re-implementation that ignores the READ routine, not a lazy port. The design claim in section 5 ("ignoring C3/C4 fails at step 4") applies to the wrong kind of shortcut. The real step 3 -> step 4 dependency is the bitwise round-trip requirement (parallel non-deterministic reductions), which is still untested.
4. Step 2 dependence (C1) and step 3 dependence (C2, C5) are still only hypotheses; they need solution B and an attempt at steps 2-3 on A before the dependency claim can be made.

Consequence for the plan: do not claim a dependency until section 5's validation protocol is run. Next experiments, in order: (a) extend A to step 2 (outflow, moving wall) and measure the edit size, (b) write a parallelized version of A and check whether it breaks the 1e-6 and bitwise requirements, (c) write solution B (refactored) and compare effort.

### 12.3 Sweep of step 2 and step 3 edit sizes on solution A (2026-11-17)

Files: `experiment/solution_A_step2/nsflow.py`, `experiment/solution_A_step3/nsflow.py` (dev only). Edit size is a proxy, not an agent-effort measurement; one author, one try, no timing of human or agent work.

**Step 2 on the literal port (inflow, outflow, moving walls):** 32 lines added on a 314-line file (diff touches 40 lines), in six places: deck variables, `setbc`, `tstep` (max velocity), both Poisson loops (outflow coefficient), `adapuv` (outflow face). All earlier cases stayed **bitwise identical** to Fortran. Analytic checks pass: Couette (linear inflow, moving top wall, outflow) matches y to 4e-14 in u; Poiseuille (parabolic inflow, outflow, 24x12) matches the analytic outlet profile to 7.9e-3 (discretization error) with pressure gradient -1.188 vs -1.2.
Reading: **C1 is weak.** The legacy code is small enough that boundary logic lives in a few places and a literal port extends cheaply. Without a larger code base or a harder step 2 (for example internal obstacles via cell flags, or mixed BCs on all sides interacting with the Poisson solve), step 2 does not punish a literal port. The dependency chain is not demonstrated at step 2.

**Step 3 on the same code (vectorized NumPy, red-black SOR):** 160 changed lines (73 added) of 338, touching every numerical kernel (`tstep` maxima, `compfg`, `comprh`, `poiss`, `adapuv`) plus storage; I/O untouched. Elementwise kernels keep exactly the same operation order, so only the SOR order and the residual reduction change results.
- Accuracy vs Fortran at step 300 (32x32 cavity, eps 1e-8): u 1.5e-10, v 2.4e-10 relative L2, dT = 0. Second deck: u 4.6e-9, v 2.5e-9. These are far inside the proposed max(1e-6, 50 x tol) band, so the tolerance policy is satisfied by this port.
- **Pressure differs by about 10% relative L2.** The pressure is defined only up to an additive constant when all walls are Neumann, and the two SOR orders settle on different constants. Verifiers must compare pressure with the mean removed (or not at all), and the restart check must not compare raw pressure.
- **Speed:** at 128x128, 30 steps, Fortran took 2.9 s and this first NumPy version 11.4 s (about 4x slower: whole-array masked updates do twice the work per sweep and allocate). A naive vectorization does not beat the legacy; reaching the S_target = 8 speedup target (relative to the verifier's own single-thread reference) needs real work (compiled kernels, blocking, threads). So the speed component is meaningful, but the baseline definition matters: if T_base is the Fortran-like sequential port, a pure-Python agent starts well below 1.
- Not tested: multithreaded determinism, large grids, the bitwise restart round trip with parallel reductions. These remain the untested core of the step 3 -> step 4 claim.

**What this changes in the plan**
1. Step 2 needs a more demanding extension or a bigger legacy code to create a real dependency (see section 9).
2. Step 3 is the real difficulty step; its dependency is mostly "restructure all kernels", which is a cost of any port, not specifically of a lazy one. The planted coupling C2 (COMMON state) did not obstruct vectorization here because we ported into explicit arrays anyway.
3. Verifier details learned: compare pressure up to a constant; define the speed baseline carefully; keep operation order in elementwise kernels or relax tolerances.
4. The dependency validation protocol (section 5) still has not been run, because solution B (refactored) and an A-vs-B effort comparison do not exist. Current evidence is, if anything, evidence against a strong dependency at steps 2-4 for this code size.

### 12.4 Legacy code enlarged: obstacles and Boussinesq temperature (2026-11-17)

New in `legacy/` (now 583 lines including `common.inc`, up from about 450; **still far below the 6-10k target**):
- **Rectangular obstacles** (up to two blocks, cell-index ranges in the deck). A cell-flag array replaces the index tests in the Poisson solver (neighbour coefficients come from `FLAG`), `COMPFG` and `ADAPUV` skip non-fluid faces, and `SETBC` adds obstacle no-slip handling (mirrored tangential ghost values, blocked normal faces, with an ambiguous rule at corners). Boundary logic now lives in five routines instead of two. `NFLUID` replaces `IMAX*JMAX` in the residual norm.
- **Boussinesq temperature** (`temp.f`): cell-centred field, blended donor-cell convection, diffusion with `PEC`, buoyancy term in `G`, fixed-temperature or adiabatic side walls, adiabatic obstacles, thermal diffusion added to the time-step limit, Nusselt number printed at the end. Restart format version 3 appends a temperature record; version 2 files (no temperature) are still read, and a temperature run restarted from one starts with T = 0.

Checks (all run on the new binary):
- With obstacles and temperature switched off, outputs and restart files are **bitwise identical** to the previous version on two cavity decks.
- Differentially heated cavity, Ra = 1e3, Pr = 0.71 (de Vahl Davis): Nu = 1.1236 at 32^2 and 1.1201 at 64^2 (reference 1.118); peak velocities within about 1% of the reference at 32^2 and 0.4% at 64^2 (u: 3.613 / 3.635 vs 3.649; v: 3.671 / 3.685 vs 3.697), peak positions within one cell. Velocity scaling: velocities in units of sqrt(g beta dT L), multiplied by sqrt(Ra Pr) to compare.
- Lid-driven cavity with two internal blocks (40x40, Re = 200, T = 30): finite, velocities inside block interiors exactly zero. No quantitative reference.
- Restart: temperature run restarted from its own v3 file works; a v2 file read into a temperature run works. The numerical effect of the v2 -> v3 mismatch has not been measured.

**Consequences**
1. The step 2/3 edit sizes in 12.3 are **stale**: they were measured on the smaller code, and solution A (Python) does not yet implement obstacles, temperature or restart v3, so it no longer matches the reference. A must be updated (flags in the Poisson solver and fluxes, obstacle BCs, temperature, restart v3) and re-verified bitwise before any new sweep.
2. Step 2 inflow/outflow in this version touches more places than before: the flag-based pressure coefficients need an outflow (Dirichlet) cell type, `COMPFG`/`ADAPUV` need outflow faces, `SETBC` needs inflow, and `SETBT` needs inflow temperature handling. Whether that is enough to separate a literal port from a refactored one is still unmeasured.
3. Candidate hidden-case families for step 1 now include: cavity variants, cavities with obstacles, and differentially heated cavities (Nu and peak velocities against the benchmark, with the pressure compared up to a constant).
4. Remaining gap to the planned scale: no turbulence closure or variable properties, no inflow/outflow in the legacy (by design), grid size capped by `MX`. Legacy code is about 600 lines, not 6-10k; more features or a different base problem would be needed to approach that scale, and the first-trials rule (section 9) still applies.

Supersedes the numbers in 12.3. Files: `experiment/solution_A_v1/` (literal port of the enlarged code), `solution_A_v1_step2/`, `solution_A_v1_step3/`. Same caveats: edit size is a proxy, one author, one try, no effort measurement.

**Step 2 (inflow, outflow, moving walls) on A_v1:** 34 lines added (40 changed) on 452, in the same six places as before. Regression: bitwise identical to Fortran on the plain, obstacle and heated-obstacle cases. **What this means for the plan (honest assessment)**
1. **Step 1-2 are not discriminating.** A literal port, which needs no numerical insight, matches bitwise at step 1, and step 2 costs it about 35 lines. The task as designed does not separate a lazy port from a refactored one at these steps.
2. **Step 3 is the real work**, but its cost (rewrite nearly all kernels, about 300 lines here) is the same for any port; the planted C2 coupling did not obstruct vectorization (the NumPy port uses explicit arrays and an independent SOR order). Whether threads or compiled kernels change that is untested.
3. **Step 4's restart check mostly tests copying the READ routine** (see 12.2).
4. The dependency claim (README/DESIGN section 5) is **not supported** by the evidence so far. The remaining honest options are: (a) make later steps far larger or genuinely entangled with earlier design choices (for example the extension forces a data structure the literal port cannot absorb); (b) drop the claim and position the task as a long-horizon multi-step port with numerical-science oracles; (c) pick a different base problem in which the legacy hides state that a port must discover rather than copy. This is a design decision to take before more building.
5. Verifier requirements confirmed: compare pressure demeaned over fluid cells; compare u, v, T at fixed step counts and T, dt-sequence for restarts; speed baseline must be defined against a compiled single-thread reference, not a pure Python port.

## 13. Redesign v4: black-box vendor releases, graded characterization suite (2026-11-17)

### 13.1 Diagnosis
The evidence in 12.2-12.5 refutes the planted-coupling dependency (section 5): with source available, the Fortran **is** the specification, so a literal port needs no understanding, matches bitwise, extends cheaply (about 35 lines for step 2) and parallelizes without touching the coupling. Two further facts from the mutant experiment below:
- Lexicographic SOR in either loop nesting gives **bitwise identical** results (mutant m7): both are natural orderings with the same dependency structure, so even C2/C5 were weaker than claimed; a wavefront-parallel SOR would reproduce the legacy result exactly.
- Resetting the controller history on restart (C3) is a no-op (a fresh run starts from the same values); only the dt ramp (C4) changes the trajectory (mutants m2 and m10 are killed, nothing else on restart).
The fix is not more code, it is removing the copy path.

### 13.2 Chosen direction
Change the base problem from "port this source" to **"reproduce this vendor binary"**:
1. The candidate receives a compiled vendor binary (`vendor/nsflow-1.0`, stripped), an incomplete user manual (lists deck variables and file formats, not the scheme), three example decks with outputs, and example restart files. No source, no compiler for the legacy language.
2. Steps are **vendor releases**: v1.0 (cavity, free-slip, restart v2), v1.1 (obstacles, temperature, restart v3, delivered at step 2), then performance and migration at steps 3-4. The candidate extends its own implementation and may run the new binary as an oracle.
3. **The vendor binary is absent in the verifier container**, so wrapping or shelling out to it fails; the solution must be self-contained (also scan for embedded executables).
4. **The candidate also delivers a characterization suite** (decks plus expected outputs recorded from the vendor binary). The verifier (a) regenerates the expected outputs to check authenticity, (b) measures the **mutant kill rate**: how many of a hidden set of buggy vendor variants differ from the golden outputs on at least one suite case. Suite quality is graded cumulatively across releases (v1.0 mutants at step 1, v1.0+v1.1 mutants from step 2 on).
5. Hidden-case fidelity (fields at 1e-6, T and dt sequence, restarts) is graded as before, plus pressure demeaned over fluid cells.

### 13.3 Why this creates real dependencies
- **Model carry-over:** the scheme identified in step 1 (convection blend, dt controller, boundary rules) is what step 2 extends. A model fitted to the v1.0 examples but wrong in untested details shows up as errors in v1.1 features and in hidden decks.
- **Semantic ambiguity that must be probed, not copied:** obstacle corner rules, ramp length after restart, thermal dt limit, residual normalization with obstacles: none is documented, each is a hidden-case discriminator (see matrix below).
- **Own artifacts carry over:** the suite from step 1 is the safety net for step 3 (performance rewrite) and the evidence for step 4; its kill rate is graded again in later steps.

### 13.6 Risks (unmeasured unless stated)
1. **Step 1 may be too hard or unidentifiable.** Reaching 1e-6 from a black box depends on how well the scheme can be identified from experiments. Nobody has attempted it; this is the key unknown and needs a pilot with an agent that has no source.
2. **Decompilation shortcut:** a stripped gfortran binary can be disassembled, giving a (hard) copy path. It is also real reverse engineering and not free, but it should be listed as YELLOW; mitigations: no disassembler in the image, compile at higher optimization.
3. **Mutant set design:** equivalent mutants, unfair mutants (behaviours the manual implies), and gaming (a suite padded with many decks). Needs a rule such as a case budget.
4. **Oracle access:** the candidate can generate unlimited reference data from the binary; this is intended, but the hidden decks must be drawn from a distribution it cannot enumerate.
5. **Realism:** reverse engineering a binary is real work (lost source, vendor dependence), but less common than porting source; to be argued in the README.
6. The old code-scale gap remains (about 600 lines of legacy behaviour); black-box identification probably makes a small code harder than a large one is to read, but this is a hypothesis.

### 13.7 Not chosen, kept as alternatives
- **Keep the source, make step requirements entangled** (e.g. force data structures a literal port cannot absorb): hard to do without contrivance, and every attempt so far was absorbed cheaply.
- **Fixed downstream agent as a maintainability judge** (a reference agent must extend the candidate's code within a budget): objective in principle, noisy and expensive.
- **Drop the dependency claim** and call it a multi-step port task: honest, but weakly differentiated from FrontierSWE's `pw.x`.

2. Write 15-30 mutants, mark equivalents, fix a case-budget rule, define the kill-rate scoring.

### 14.3 Conclusions
1. **Step 1 in this form is too easy.** A single agent reached round-off agreement on essentially all hidden decks in under 150 tool calls. The scheme is a textbook staggered projection method (the agent recognised it as NaSt2D-style) with a handful of quirks, all discoverable by black-box probing. The black-box redesign removes the copy path, but at this scale and with this algorithm it does not make step 1 hard; it also does not give a week-long horizon.
2. **Textbook-ness is a confound.** The legacy code is modelled on a published method, so recognition rather than discovery explains much of the success. A task meant to be hard needs a scheme that is not in textbooks or training data.
3. **The planted hidden state is mostly inert.** DECAY/UMAXH never changed any result; the restart ramp was found quickly because restart is an obvious thing to probe.
4. **The suite score still discriminates** (4 of 5) and exposed a real gap (the unreachable-regime parameter), but with so few cavity mutants it cannot yet carry a task.
5. **Step 3 (performance) is where the difficulty now sits**, as the candidate's solver is 100x slower than the vendor's compiled code; the pilot environment could not link C, so this is an environment artifact, but it indicates the real gap between working and fast.
6. Unmeasured: steps 2-4 under the black-box design, the effect of a larger or less standard legacy code, and variance between agents.

### 14.4 Options before more building
- **Make the hidden system harder, not just closed:** a non-textbook scheme (unusual discretization, implicit time stepping with a nonstandard nonlinear solve, adaptive mesh or multi-rate stepping), many interacting modes so that the deck space cannot be probed exhaustively, and state that matters in reachable regimes.
- **Make later steps the difficulty:** performance to a compiled-code baseline (with a working compiler in the image), scale-up to 3D or large grids, and a fidelity target tighter than round-off conventions allow (bitwise reproducibility under parallelism).
- **Increase scale of the black box:** many releases, each adding features with ambiguous semantics.
- **Accept a mid-difficulty task** and position it as a benchmark of careful black-box reproduction, then raise difficulty with steps 3-4 only.

## 15. NSFLOW 2: a non-textbook scheme (2026-11-17)

New legacy code in `legacy2/` (cavity-only, about 400 lines), replacing the textbook projection scheme of `legacy/` as the black-box target. Purpose: remove "recognise a published method" as a shortcut, and make the hidden controller state matter in reachable regimes. `legacy/` (obstacles, temperature) is kept as a later "release" candidate.

Scheme (idiosyncratic on purpose; none of this is in the manual):
- **Convection:** face value = central average corrected toward the upwind side by the weight `w = Pe / (Pe + AUP)`, with `Pe = |a| * h * Re` (cell Peclet number), applied separately at every face and for both components; `AUP` is a deck variable (default 2.3).
- **Time stepping:** Euler predictor, trapezoidal corrector, embedded error estimate (their difference, normalised by `1e-3 + max|velocity|` and by `TOL`), then projection of the corrector result.
- **Step-size control:** PI controller `dt_next = dt * 0.9 * err^-0.3 * (err_prev/err)^0.2`, growth clipped to [0.3, 1.5], with hard caps from a convective limit `CFLMAX*min(dx,dy)/umax` and a diffusive limit. Hidden state: `dt_next` and `err_prev`; **a restart resets them** (to the deck `DT0` and 1), so the continuation depends on `DT0` and differs from an uninterrupted run.
- **Pressure solver:** x-line relaxation (tridiagonal solve per row, relaxation factor `OMEGA`), natural boundary conditions, residual stopping rule. The iterate path matters only at loose `EPS`.

Checks (Fortran, my runs): finite and stable for Re = 100 (32x32), Re = 1000 (48x48), TOL = 1e-3, 1e-2, 3e-2; Re = 100 32x32 lid-driven cavity centerline extrema u_min -0.2021 (Ghia -0.2109; 3% coarse-grid error), v_max 0.1721 (0.1753), v_min -0.2431 (-0.2453); restart at step 100 vs uninterrupted differs by T 3.6939 vs 3.6727 and relative L2 1.2e-3 in u (reachable, consequential, unlike the earlier DECAY state). Default `TOL` set to 1e-2 (4450 steps to T = 20 at 32x32).
Mutants for the suite score: `scripts/make_mutants2.py` (10 variants: weight function, controller exponent and safety factor, restart state, error scaling floor, diffusion cap, free-slip sign, growth cap, convective cap, corrector weight), `experiment/mutants2/`. Equivalence not yet checked.
Pilot 2 (fresh agent, `pilot2/` in the scratchpad, manual with the new variables, small examples) was started; evaluation script `scripts/eval_pilot2.py`. Results: see the next section once the run finishes.

### 16.2 What the agent reported (not verified by me)
28 tool calls and about nine minutes (the harness numbers). ### 16.3 Conclusions
1. **The non-textbook scheme did not make the task harder.** Disassembling about 400 lines of compiled Fortran is quick, so the scheme's novelty is irrelevant once disassembly is allowed. Pilot 1 (no disassembly, textbook scheme) was also solved. In both pilots the whole of step 1 took tens of tool calls.
2. **Closing the source does not create a long horizon.** Whether the specification is a source file or a disassembly, a code of this size is reproduced within minutes to hours by an agent. Stripping symbols or removing disassemblers would only raise the cost modestly (an arms race that does not match the "realistic engineering" goal, and an agent can still decode the instruction stream).
3. **The root problem is scale, not secrecy.** A few hundred lines of one algorithm is not a week of work. Black-box vs source, textbook vs idiosyncratic scheme, none of these change that.
4. **Suite score:** discriminating (4/5 and 8/10) and the survivors are informative (regime-specific behaviour), but it measures test design, not the difficulty of the central work.
5. The mutant and comparator machinery, the hidden-deck evaluators and the restart/fidelity measurements are reusable for any other base.

### 16.4 What this means for the plan
The four-step design (reproduce, extend, accelerate, migrate) is sound as a structure, but the base problem is too small to hold a week-long horizon. Options:
- **Use a real, mid-to-large open-source legacy code (roughly 10k-100k lines of Fortran or C, permissive license) as the base.** Scale and genuine undocumented behaviour then come for free; the oracle is the original code built in the verifier container; steps 2-4 are real feature, performance and format-migration tasks on that code. Cost: choosing the code, checking the license, building references and hidden cases; overlap with FrontierSWE's Quantum ESPRESSO task in the porting pattern (but not in domain or in the multi-step structure).
- **Scale the synthetic code by an order of magnitude or two** (many models, solvers and I/O formats). Costly to write well, and risks looking contrived.
- **Drop the legacy-port framing** for a different long-horizon problem where hardness comes from the problem itself (for example performance against an expert-tuned baseline, or a research-style open problem with a scored curve); keep the multi-step verifier machinery.
- Keep the present code only as a small demonstration or tutorial task.

#### 17.6.1 Diagnosis of the pilot-5 failures

  - 7 are floppy species (acetate, dimethyl sulfide, DMSO, toluene, trimethylphosphine, chloroethane, methanethiol). MOPAC's own symmetry shortcut changes its answer relative to the same job with NOSYM by 127 cm-1 (acetate), 92 (toluene), 48 (DMS), 19 (trimethylphosphine), even with the geometry re-optimized to GNORM 0.0005 (LET). Toluene's lowest mode is -77 cm-1 with symmetry and +16 cm-1 without. So the reference value of these cases is partly an artifact of MOPAC's symmetrized-Hessian code path, not physics. With NOSYM the agent matches MOPAC's NOSYM output to 0.2 to 1.1 cm-1 (14.5 for acetate, a very soft 8.7 vs 23.2 cm-1 torsion, and 6.5 for methoxy). The agent reproduces MOPAC's rule only approximately (operation order, which atoms are skipped).
  - 3 are near-tolerance noise (benzene 0.13, phosphine 0.15, hydronium 0.065 cm-1 vs the 0.05 tolerance): MOPAC sym-vs-nosym differs by 0.25 cm-1 for them; the agent's NOSYM match is 0.03 to 0.09 cm-1. The tolerance for such cases is simply too tight for finite-difference emulation.
- Consequence for the task design: a FORCE verifier that asks to reproduce MOPAC to 0.05 cm-1 on low-symmetry floppy molecules rewards imitating a buggy shortcut. Either restrict the hidden set to molecules where MOPAC sym and NOSYM agree to within the tolerance (rigid molecules), set per-mode tolerances from the sym/NOSYM spread, or deliberately make symmetry emulation part of the task and say so. This must be settled before step 2 is gradable.

#### 17.6.2 Decision on symmetry emulation
- Decision (2026-11-19, author): reproducing MOPAC's symmetry-based Hessian shortcut is part of step 2's grading. The task text will say that the reference is the original program's output including its point-group detection and symmetry-equivalent-atom shortcuts (bug-for-bug compatibility, as in real legacy migration), and the hidden set deliberately includes low-symmetry floppy molecules where that shortcut changes MOPAC's own answer by tens of cm-1 relative to `NOSYM`. Frequency tolerance becomes 0.2 cm-1 (finite-difference emulation floor; the agent's NOSYM match was 0.03 to 0.09 on rigid molecules, so 0.05 was below the noise floor); ZPE tolerance stays 1e-3 kcal/mol.
- Rescoring the existing pilot-5 output at 0.2 cm-1: hidden 24/32 all quantities (frequencies 24/32, ZPE 24/32, heat 32/32); at 1.0 cm-1 frequencies 25/32. The 8 remaining failures are exactly the symmetry-emulation gap: acetate, dimethyl sulfide, DMSO, methoxy radical (wrong point group), toluene, trimethylphosphine, chloroethane, methanethiol. Not yet re-run with the changed task text, so whether an agent told about the requirement closes the gap is UNVERIFIED.
- Honest risk: grading on a vendor shortcut that gives unphysical values (toluene -77 vs +16 cm-1) is a design choice that some reviewers may reject as oracle-fitting; the argument for it is that faithful porting of legacy code means preserving its observable behavior, and a faithful port is detectable only by such cases. It also makes the step depend on deep, source-level reading, which is the intended horizon driver.

### 17.8 Pilot 7: tightened step 3 and step 4

Same method as the earlier pilots (fresh agent, source only, numpy/scipy, own evaluation against private MOPAC references; `scripts/make_pilot6b.py`, `make_pilot7.py`, `zmat.py`, `eval_pilot7.py`). The agent started from the pilot-6 solver and worked ~25 min wall, ~50 tool calls.
