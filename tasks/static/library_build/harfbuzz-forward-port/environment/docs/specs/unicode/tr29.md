# UAX #29 - Unicode Text Segmentation
Source: UAX #29: Unicode Text Segmentation, https://www.unicode.org/reports/tr29/tr29-49.html
These notes restate the source's structures and rules; where they differ, the source governs.

Version digested: Unicode Standard Annex #29 for Unicode 18.0.0, revision 49, dated
2026-09-01. The latest revision is always at https://www.unicode.org/reports/tr29/.

The annex defines default boundaries for three kinds of text element: grapheme clusters
(user-perceived characters), words and sentences. Line breaking is defined elsewhere
(UAX #14). This digest gives the grapheme cluster specification in full and the word and
sentence specifications in compact form.

## Notation used in this digest

The source writes rules with non-ASCII symbols. This digest uses the following ASCII forms.

| Source symbol | Written here | Meaning |
|---|---|---|
| division sign | `/` | A boundary is allowed here (break). |
| multiplication sign | `x` | No boundary here (do not break). |
| rightwards arrow | `->` | The left-hand sequence is handled exactly like the right-hand side. |
| not sign | `NOT` | Complement of a set of property values (matches one character not in the set). |
| not-equal sign | `!=` | Property value differs. |

Other notation, as in the source:

- `sot` and `eot` stand for start of text and end of text.
- `Any` matches any code point; it is not a property value.
- Property values (CR, Extend, ALetter, ...) stand for any character with that value.
- `( A | B )` is alternation; for an alternation the first match is taken. `*`, `+`, `?` are
  the usual repetition operators.
- `[^RI]` matches one character that is not RI. `\p{Prop=Value}` is a property match;
  inside square brackets, `-` is set difference and `&` is intersection (UnicodeSet
  notation).
- In the rule listings below the columns are: rule number, left side, operator, right side.
  Either side may be empty.

## How rules are evaluated

- Each specification first assigns every character one property value from its table. The
  values are disjoint, except Any. If a character fits several rows, the row nearer the top of
  the table wins. The UCD data files (GraphemeBreakProperty.txt, WordBreakProperty.txt,
  SentenceBreakProperty.txt and related files) hold the normative assignments; the tables in
  the annex, and below, only summarize them.
- The rules form an ordered list. To decide whether a given offset is a boundary, try the
  rules from the first downwards; the first rule that matches at that offset decides
  (boundary or no boundary) and matching stops. Every rule after the first therefore
  carries an implicit "otherwise".
- Each rule has exactly one boundary position (its operator). Negation is used only where it
  resolves to a single character. Degenerate input (for example a combining mark after a
  letter of another script) gets no special treatment, and script changes are not
  boundaries by default; an implementation that breaks at script changes should use
  Script_Extensions and handle Common and Inherited properly.
- The rules describe results, not an algorithm. Implementations commonly compile them into
  state tables (deterministic finite-state machines); the result must be the same.

## Conformance

- UAX29-C1 (extended grapheme cluster boundaries): either use the UCD property values with
  the extended rules of section 3.1 (C1-1), or declare a profile of C1-1 with an exact
  description of changed property values, rules or programmatic overrides (C1-2). Legacy
  grapheme clusters are one profile of this kind.
- UAX29-C2 (word boundaries) and UAX29-C3 (sentence boundaries) have the same two options,
  with the rules of sections 4.1 and 5.1 respectively.
- The default rules may be tailored for locales (a profile may add and remove boundaries);
  languages such as Thai, Lao, Chinese and Japanese need dictionary-based word breaking.
  Locale-specific rules from CLDR are preferred where they exist, and CLDR's extended rules
  are recommended for best handling of emoji zwj sequences.
- All rules are defined on NFD text. Because no boundary falls inside a combining character
  sequence or conjoining sequence, the default rules give the same boundaries when applied
  directly to non-NFD text (tailored rules might not).

## Grapheme clusters

### Legacy and extended grapheme clusters

- A legacy grapheme cluster is a base followed by zero or more continuing characters. The
  base is a single character, a sequence of Hangul jamo forming one syllable (definition
  D133 of the Unicode Standard), or a pair of Regional_Indicator characters. Continuing
  characters are nonspacing marks, the two join controls (U+200C ZERO WIDTH NON-JOINER,
  U+200D ZERO WIDTH JOINER) and a few spacing marks needed for canonical equivalence. ZWNJ
  is in Extend because in Bangla, Khmer, Malayalam and Odia it can sit between a consonant
  and a virama or other mark, where no break is wanted. Degenerate cases (an isolated
  control or combining mark) still form clusters so that any text can be segmented.
- An extended grapheme cluster adds: all spacing combining marks (for example U+093F
  DEVANAGARI VOWEL SIGN I) as continuing characters, Prepend characters before the base,
  and the InCB conjunct rule GB9c. Extended clusters are the default and are recommended;
  the legacy variant is used only where an environment requires it.
- Difference between the variants: legacy clusters exclude rules GB9a, GB9b and GB9c;
  extended clusters include them. A citation of the Unicode definition must say which
  variant is meant.
- Clusters are identical for all canonically equivalent forms of a text (NFC or NFD).
- Default word and sentence boundaries never fall inside a grapheme cluster. Line breaks
  usually do not either, except for special handling of spaces described in UAX #14.
- A grapheme cluster is not a ligature and need not match glyphs: <f, i> shown as one
  ligature glyph is still two clusters. Clusters have no size limit. Unassigned (Cn) and
  private-use (Co) code points get property values anticipating likely use.

### Table 1b: combining character sequences and grapheme clusters as regular expressions

Identifiers starting with a lowercase letter are defined in Table 1c; those starting with an
uppercase letter are Grapheme_Cluster_Break values. For alternation, the first match wins.

| Term | Regex | Remarks |
|---|---|---|
| combining character sequence | `ccs-base? ccs-extend+` | One combining mark alone counts (degenerate); one base character alone does not. |
| extended combining character sequence | `extended_base? ccs-extend+` | extended_base adds Hangul syllables. |
| legacy grapheme cluster | `crlf \| Control \| legacy-core legacy-postcore*` | One base character alone is a cluster; isolated non-base characters and controls are degenerate clusters. |
| extended grapheme cluster | `crlf \| Control \| precore* core postcore*` | Adds Prepend characters and spacing marks. |

### Table 1c: regex definitions

```
ccs-base             := [\p{L}\p{N}\p{P}\p{S}\p{Zs}]
ccs-extend           := [\p{M}\p{Join_Control}]
extended_base        := ccs-base | hangul-syllable
crlf                 := CR LF | CR | LF
legacy-core          := hangul-syllable | RI-Sequence | xpicto-sequence
                        | [^Control CR LF Extend ZWJ] | legacy-postcore
legacy-postcore      := [Extend ZWJ]
core                 := hangul-syllable | RI-Sequence | xpicto-sequence
                        | core-linker-conjunct
                        | [^Control CR LF Extend ZWJ SpacingMark] | postcore
postcore             := conjunct-extension | [Extend ZWJ SpacingMark]
precore              := Prepend
RI-Sequence          := RI RI
hangul-syllable      := L* (V+ | LV V* | LVT) T* | L+ | T+
xpicto-sequence      := \p{Extended_Pictographic} (Extend* ZWJ \p{Extended_Pictographic})*
core-linker-conjunct := [\p{InCB=Linker} - Extend] \p{InCB=Extend}* \p{InCB=Consonant}
conjunct-extension   := [\p{InCB=Linker} & Extend] \p{InCB=Extend}* \p{InCB=Consonant}
```

The regular expression must be matched starting from a known boundary (for example the
start of the text); it then finds the next boundary.

Other properties used by the grapheme rules:

- Extended_Pictographic: the emoji property of that name (Unicode emoji data, UTS #51).
- Indic_Conjunct_Break (InCB), values Linker, Consonant and Extend (all other characters have
  the value None): a UCD property (DerivedCoreProperties.txt). Rule GB9c and the Table 1c
  definitions use it; the annex itself does not list its members.
- V is wider than Hangul vowel jamo: characters of other scripts that bind tightly without
  depending on a base (conjoining behaviour, such as the Kirat Rai vowel signs listed above)
  are given V.
- Grapheme_Extend = Yes is the source of Extend. Grapheme_Base is no longer used by the
  annex.

### Grapheme cluster boundary rules (GB1 to GB999)

Rules marked EG apply to extended grapheme clusters only (legacy clusters skip them).

```
Boundaries at sot and at eot, except in empty text:
GB1     sot                                    /   Any
GB2     Any                                    /   eot

No boundary between CR and LF; elsewhere, a boundary before and after every Control, CR and LF:
GB3     CR                                     x   LF
GB4     (Control | CR | LF)                    /
GB5                                            /   (Control | CR | LF)

Keep Hangul syllables and other conjoining sequences together:
GB6     L                                      x   (L | V | LV | LVT)
GB7     (LV | V)                               x   (V | T)
GB8     (LVT | T)                              x   T

No break before extending characters or ZWJ:
GB9                                            x   (Extend | ZWJ)

EG only - no break before spacing marks or after Prepend characters:
GB9a                                           x   SpacingMark
GB9b    Prepend                                x

EG only - no break inside certain InCB=Linker combinations:
GB9c    \p{InCB=Linker} \p{InCB=Extend}*       x   \p{InCB=Consonant}

Keep emoji modifier sequences and emoji zwj sequences whole:
GB11    \p{Extended_Pictographic} Extend* ZWJ  x   \p{Extended_Pictographic}

No break inside emoji flag sequences (between RI characters when an odd
number of RI characters precede the position):
GB12    sot (RI RI)* RI                        x   RI
GB13    [^RI] (RI RI)* RI                      x   RI

Otherwise break everywhere:
GB999   Any                                    /   Any
```

Notes on the rules:

- There is no GB10; numbering jumps from GB9c to GB11.
- GB9c changed in revision 49 (Unicode 18.0.0): it now reads
  `\p{InCB=Linker} \p{InCB=Extend}* x \p{InCB=Consonant}`, with no requirement for a
  preceding InCB=Consonant. Table 1c's core-linker-conjunct and conjunct-extension express
  the same change in regex form.
- GB12 and GB13 pair regional indicators from the left: in a run of RI characters, the
  boundary falls after every second one.
- Every RGI emoji sequence (UTS #51, ED-17 and ED-27) is one grapheme cluster, so clusters
  can support editing of RGI emoji sequences. Some valid but not recommended emoji sequences
  span several clusters.
- The rules convert directly into a regular expression (Table 1b, Table 1c) and from there
  into a deterministic state machine.

## Word boundaries (compact)

Default word boundaries put breaks around most characters that are not parts of words
(punctuation, spaces), keep letters, digits and certain inner punctuation together, and break
around each ideograph. Scripts written without spaces (Thai, Lao, Khmer, Myanmar, Chinese,
Japanese and similar) need tailoring, typically with a dictionary. Hangul is handled like
Latin for word boundaries.

  rules, except directly after sot, CR, LF and Newline; it also implies

- Common tailorings mentioned by the source: a rule WB5a `apostrophe / vowels` for French and

  (U+002D, U+055A, U+058A, U+0F0B, U+1806, U+2010, U+2011, U+201B, U+30A0, U+30FB, U+FE63,
  U+FF0D) to MidLetter; adding spaces used as thousands separators (U+0020, U+00A0, U+2007,
  U+2008, U+2009, U+202F) to MidNum; treating U+0022 between Hebrew letters as MidLetter.
  Format characters are kept with a preceding word character but do not start a word
  (<LRM><ALetter> breaks before the letter).

### Sentence boundary rules

```
SB1     sot                                  /   Any
SB2     Any                                  /   eot
SB3     CR                                   x   LF
SB4     ParaSep                              /
SB5     X (Extend | Format)*                 ->  X
SB6     ATerm                                x   Numeric
SB7     (Upper | Lower) ATerm                x   Upper
SB8     ATerm Close* Sp*                     x   ( NOT(OLetter | Upper | Lower | ParaSep | SATerm) )* Lower
SB8a    SATerm Close* Sp*                    x   (SContinue | SATerm)
SB9     SATerm Close*                        x   (Close | Sp | ParaSep)
SB10    SATerm Close* Sp*                    x   (Sp | ParaSep)
SB11    SATerm Close* Sp* ParaSep?           /
SB998   Any                                  x   Any
```

- SB5 ignores Extend and Format except after sot, after ParaSep and inside CR LF; it also
  implies `Any x (Format | Extend)`.
- SB6 to SB8 suppress breaks after an ambiguous terminator (mainly FULL STOP) before a
  number, between uppercase letters, before a lowercase letter (possibly after other
  punctuation) and before continuation punctuation; SB8a covers SContinue and repeated
  terminators. Abbreviations such as "Mr." followed by a capitalized name are not detected
  without tailoring.
- SB9 to SB11 break after the whole sequence `SATerm Close* Sp* ParaSep?`, never inside it.
- Note that the final rule is SB998 ("otherwise do not break"), not a break-everywhere rule.
- A word segment can, rarely, span a sentence boundary; tailoring SB11 for scripts written
  without spaces reduces such conflicts.

## Ignore rules (WB4, SB5) as rewrites

WB4 and SB5 make a whole grapheme cluster act as one character in word and sentence
segmentation (so L, V, T, LV and LVT sequences, marks and Format characters do not split
words or sentences). An implementation can replace such a rule by rewriting the rules:

1. Replace the ignore rule by `(NOT Sep) x (Extend | Format)` for SB5; that is, no break
   before an ignored character except after the separators the rule names. For WB4 the set
   is (Extend | Format | ZWJ) and the excluded left contexts are sot, CR, LF and Newline.
2. In every later rule, insert `(Extend | Format)*` after each property value, except inside
   negations and except after the last item on the right side. For example
   `X Y x Z W` becomes
   `X (Extend | Format)* Y (Extend | Format)* x Z (Extend | Format)* W`.
3. An alternation that matches one character is extended as a whole:
   `(STerm | ATerm)` becomes `(STerm | ATerm) (Extend | Format)*`, not an alternation of
   separately extended members.

Tailorings should leave the ignore rules alone, except perhaps for moving some Format
characters into other classes.

## Implementation notes

- Normalization: input need not be normalized. The grapheme rules never break inside a run
  of nonspacing marks or between a base and its nonspacing marks, and a few characters
  (U+09BE BENGALI VOWEL SIGN AA is one) are given Extend explicitly, so canonically
  equivalent texts get equivalent boundaries. Word and sentence rules never break inside a
  grapheme cluster and treat each cluster with one property value.
- Random access: to find boundaries near an arbitrary offset, first move backwards with a
  separate, conservative set of "safe point" rules to a position known to be a boundary,
  then run the normal rules forwards, discarding boundaries before the requested offset. A
  reverse state table built from the same rules supports backward iteration.
- Tailoring by data: map characters to property values through a table (for example a trie),
  optionally followed by a small per-language remapping table; or map some characters to
  special values that make the state machine stop and hand over to custom code (for example
  a Thai or Lao dictionary breaker), caching the results.
- Rule numbers can change between versions of the annex. The UCD's sample boundary files
  number rules in decimal form instead (WB13a is 13.1, WB13b is 13.2, SB8a is 8.1, GB999 and
  WB999 are 999.0; a rule spanning several lines gets hundredths such as 21.01, 21.02).
- Looking only at a pair of adjacent characters is not enough to decide a boundary; the rules
  need wider context (for example GB11, GB12, GB13, WB6, WB7 and SB8).

## Hangul syllable boundaries (section 8)

L, V, T, LV and LVT are Hangul_Syllable_Type values; M stands for a combining mark. For
syllable boundaries an LV syllable behaves like L V, and an LVT syllable like L V T.

Table 6, pairs never separated by a syllable break:

| Do not break between | and | Pairs |
|---|---|---|
| L | L, V, LV or LVT | L x L, L x V, L x LV, L x LVT |
| V or LV | V or T | V x V, V x T, LV x V, LV x T |
| T or LVT | T | T x T, LVT x T |
| Jamo, LV or LVT | Combining marks | L x M, V x M, T x M, LV x M, LVT x M |

All other positions before and after a jamo or precomposed syllable are syllable breaks. A
combining mark between two jamo keeps them from joining into one block.

- A syllable block can contain a precomposed syllable in the middle even in NFC (for example
  L LVT T). Every well-formed modern syllable has the form L V T? and is a single
  precomposed character in NFC.
- Standard Korean syllable block: one or more L, then one or more V, then zero or more T, or
  anything canonically equivalent. Decomposed form: `L+ V+ T*`. Including precomposed
  syllables: `(L+ V+ T*) | (L* LV V* T*) | (L* LVT T*)`. Precomposed LV and LVT syllables
  are standard blocks; choseong and jungseong fillers may stand for a missing leading
  consonant or vowel.
- KS X 1026-1 allows only single L, V and T in a syllable; conforming implementations tailor
  the grapheme rules accordingly.
- Converting a non-standard jamo sequence to standard syllables: find the syllable breaks,
  then insert fillers (Lf = choseong filler, Vf = jungseong filler) in each syllable; `[^X]`
  below means a character other than X or no character at all:

```
L [^V]   ->  L Vf [^V]
[^L] V   ->  [^L] Lf V
[^V] T   ->  [^V] Lf Vf T
```

  For example, the non-standard sequence LLTTVVTTVVLLVV splits into
  LL / TT / VVTT / VV / LLVV and becomes LLVf / LfVfTT / LfVVTT / LfVV / LLVV.
